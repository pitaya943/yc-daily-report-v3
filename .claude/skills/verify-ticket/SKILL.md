# 驗證一個 ticket PR

你看不到 Builder 的對話，這是刻意的。只根據 ticket 檔、規格、diff 與你自己執行的結果判斷。Builder 在 PR 說明裡的說法不是證據。

## 檢查表

每一項寫出「通過」或「不通過」，並附證據：你自己執行的指令與輸出、檔案與行號；有畫面的功能要你自己操作並截圖，存到 `docs/evidence/<ticket 編號>/verify/`（把這些截圖提交到 PR 分支是你唯一可以推送的內容）。沒有證據的項目算不通過。Builder 提供的證據要重做一次，不能直接引用。

1. **乾淨重跑。** 從乾淨的 checkout 安裝、套用 migration、執行全部測試。結果與 CI 一致。
2. **完成條件。** Ticket 列出的每個規則 ID 都在 `tests/implemented.txt`；每個 scenario 都被收集並通過；數量與 ticket 寫的相同。
3. **規格沒被動。** `spec/**` 與其他唯讀路徑沒有變更。
4. **範圍。** 每個變更的檔案都在 `allowed_paths` 內。
5. **測試沒被弱化。** 沒有跳過或預期失敗的標記；沒有被刪除或放寬的斷言。
6. **步驟是真的。** 逐一讀步驟實作：`When` 真的呼叫產品程式；`Then` 真的檢查結果；「nothing is written」比對的是資料庫內容。
7. **變異抽查。** 挑三條規則（優先挑金額、權限、狀態轉移），各自在本地故意改壞對應的產品程式，確認對應的 scenario 會失敗。做完還原，不要推送。
8. **拒絕案例。** 抽查五個拒絕 scenario：結果類別、完整錯誤字串、資料沒有變動，三項都有斷言。錯誤字串與 `spec/appendix-b-fields.md` 逐字相符。
9. **伺服器驗證。** 直接送出繞過介面的請求（缺欄位、超出範圍、別人的資料），確認被拒絕。
10. **規則本身。** 讀規格的規則文字，想兩個 scenario 沒列出的邊界情況，實際試。結果不合規則時是 FAIL；規格沒有說清楚時不是 FAIL，寫進「規格問題」。
11. **不可違反的規則。** `AGENTS.md`「不可違反」的每一條。

## 判定

- 全部通過：**PASS**。
- 任何一項不通過：**FAIL**，列出每個問題的位置、重現方式、預期與實際。不要提供修正的程式碼。

## 輸出

一則 PR 留言，用繁體中文：

```
## 驗證結果：PASS / FAIL

模型：（名稱與版本，從 session 的實際設定取得）
輪次：第 N 輪

| # | 檢查 | 結果 | 證據 |
| --- | --- | --- | --- |

## 問題（FAIL 時）

## 規格問題（有的話）

## 想加入 docs/pitfalls.md 的提議（有的話）
```

## 不要做

- 不要修改產品程式或測試。
- 不要憑印象填寫模型名稱；取不到時寫「無法取得」並說明原因。
- 不要因為 CI 是綠的就判定 PASS。
- 不要合併 PR。
