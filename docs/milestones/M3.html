2. 為何這樣設計

2.1 份額表是已確認數量的唯一來源（D-111、D-131）

REV-R11 要求「份額在確認時保存，且是已確認數量的唯一來源」。T-301 的 0006 建了兩張表：目錄工項的 report_shares（一列 = 一張回報、一個工項、一個人）與自訂工項的 report_custom_shares；確認當下就存下小組順位，之後成員被封存或改區也不影響（AD-7）。問題是 REV-R02、R11、R23 的 scenario 用「計算薪資」判定，而薪資在 M4。比較過兩個做法：把這三條規則移到 T-402（A），或由 T-301 提供一個只讀份額表的函式、讓步驟先呼叫它（B）。你選 B：這樣「批次確認」「兩人同時確認」「份額保存」在 M3 就有 Gherkin 把關。代價：M4 之前「has no gross」實際檢查的是「沒有已確認的份額」，比完整毛額弱；T-402 的完成條件已寫明要改接真正的薪資計算。

2.2 同一把鎖：確認、駁回、編輯、刪除、自訂工項（T-301 完成條件 8、T-302 完成條件 8）

M2 的交接指出：如果確認不和提交者的編輯用同一把鎖，兩者可以同時進行，結果是「確認後內容又被改，份額卻是舊數量」。T-301、T-302 都呼叫 report_lifecycle/repo.py 既有的上鎖函式（select … for update 鎖住那張回報），批次依 id 由小到大上鎖避免死結。T-301 的 Verifier 做了並行測試：原始程式 60 輪 0 次異常；拿掉鎖後 180 輪有 166 輪異常。

2.3 銀行帳號在應用程式內加密，不用資料庫加密（D-113）

比較過三個做法：在 T-303 一開始就加密儲存（加密會在沒有 IAM-R43 scenario 的情況下實作）、用 PostgreSQL 的 pgcrypto（要建立 extension，違反 D-045「migration 不定義函式」）、把 IAM-R14 移到 T-306 由同一張 ticket 負責儲存與加密。你選了最後一個。T-306 用 cryptography 的 AES-256-GCM，每次加密用新的隨機 nonce，金鑰在環境變數 BANK_NUMBER_KEY；資料庫只存密文（bytea，至少 42 bytes），check 約束擋掉看起來像明文的值，並保證「轉帳一定有帳號」。代價：金鑰遺失時所有帳號都無法讀取（IAM-R43 的行為），部署時要另外保管金鑰。

2.4 權限規則由一張 ticket 負責，即使要改別張的模組（D-115）

IAM-R20「只有 OWNER 能動 ADMIN」涉及 T-303（封存、復原、改區）與 T-305（重設密碼）的端點。比較過讓 T-303、T-305 各自先做好（同一條權限規則寫兩份，而且沒有 scenario 把關）或讓 T-304 依賴兩者、擴大範圍去加檢查。你選後者。T-304 的 Verifier 用 USER、ADMIN、OWNER 對每個端點實打 97 種組合，沒有疏忽也沒有誤擋。

2.5 登入與改密碼同時發生（D-141）

Cursor 的資安審查指出：登入先在沒有鎖的情況下比對密碼，之後才建立 session；如果中間密碼被改，舊密碼仍拿到一個有效的 session，D-123「改密碼後其他 session 失效」在這個時間窗沒有做到。你選擇在 T-308 修正：建立 session 前在帳戶鎖內重新確認密碼雜湊沒有改變。完成條件寫的是 for update，Builder 改用 for no key update，因為 for update 會與 sign_in_failures 外鍵的 key share 鎖死結；Verifier 用兩條連線重現了死結，也實測兩個方向仍互相等待。ticket 文字已更正。

2.6 規格裡寫明副作用，不在共用步驟開例外（D-140、D-142）

D-124 讓「改密碼時打錯目前密碼」也寫一列失敗計數，和 IAM-R30 既有兩列「資料不變」的斷言衝突（#47）；IAM-R20 有一個 scenario 用了「沒有建立帳戶」（斷言全庫不變），和 FORBIDDEN 必寫 ACCESS_DENIED 衝突（#51）。兩次都有「在共用步驟針對某句話開例外」的做法可選，你都選了改規格：把例外寫在規格裡，下一個人看得到；共用步驟維持嚴格。

2.7 CI 的時限與畫面測試（D-119、D-120、D-138）

CI 的安裝步驟原本會吞掉失敗（M2 遇過），改成 A && { B || true; } 後，T-307 第一次跑 CI 時 apt 失敗就直接在那一步顯示。T-307 在既有的 tests job 加了 Playwright 冒煙測試（D-099 的兩個畫面行為），多約 24 秒。M3 的測試數量增加後，no-weakened-tests（目標分支與 PR 各跑一輪全部測試）從約 15 分鐘增為約 25 分鐘，超過原本 20 分鐘的時限，所以 D-138 調為 45 分鐘、tests 調為 30 分鐘。

10. 這個 milestone 的學習重點

10.1 唯一來源（single source of truth）

份額在確認當下存下來，之後薪資只讀份額，不再用回報內容與目前的小組重算（REV-R11、D-111）。好處是成員封存、改區、回報被改都不會回頭改變已確認的金額；代價是任何改變份額的路徑（管理員編輯、附加自訂工項）都必須明確刪除份額並退回待確認（RPT-R12、REV-R24）。T-402 要接手的也是這個介面。

10.2 檢查與動作之間的時間窗（TOCTOU）

D-141 的漏洞是典型的 time-of-check to time-of-use：先比對密碼、之後才建立 session，中間的狀態可能已經改變。修法是在同一把鎖內「重新確認」。同樣的思路出現在三個地方：每日上限（M2）、確認與編輯（2.2）、登入與改密碼（2.5）。選鎖的時候還要注意鎖的強度：for update 會擋住外鍵檢查用的 key share，在有外鍵指向的列上容易死結，for no key update 足以排除另一個寫入者。

10.3 應用層加密與金鑰管理

AES-GCM 同時提供保密與完整性（被竄改的密文解不開），但前提是每次加密用新的 nonce。金鑰放在環境變數、不進資料庫，所以資料庫外洩也讀不到帳號；反過來，金鑰遺失就永遠讀不到，這是 IAM-R43 要規定「沒有金鑰時其他功能照常」的原因。

10.4 改規格要同時看所有既有的斷言

M3 三次停下來（#47、#51、以及 M2 的同類問題）都是「新規則與舊 scenario 的斷言矛盾」。教訓已寫進 pitfalls：Chief 記錄改變行為的決定時，要 grep 既有 scenario 中所有涉及同一張表、同一個端點的「資料不變」斷言。
