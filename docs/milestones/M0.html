2. 為何這樣設計

2.1 PostgreSQL 17，用 apt 安裝在容器內（D-033）

agent 的容器沒有 Docker daemon，所以「用 docker 起資料庫」不可行。Ubuntu 本身的 apt 只有 16，但共用 Supabase 是 17.6，所以從 PGDG（apt.postgresql.org）安裝 17，讓 migration 在本機與 Kuei 套用時的行為一致。CI 用 postgres:17 service。會出問題的情況：Supabase 升級主版本後，要同步更新 scripts/dev/install-postgres 與 workflow 的 image。

2.2 本機資料庫防線用允許清單，不用黑名單（T-001）

「不連到共用的 Supabase」（不可違反第 7 條）由 app/core/local_url.py 強制。第一版用黑名單，兩輪 Verifier 分別找到 hostaddr= 與 PGSERVICE 兩種繞過方式。最後改成 fail-closed：照 libpq 的規則解析 URI，query 參數用白名單，PGSERVICE、PGSERVICEFILE、PGSYSCONFDIR 只要有設就拒絕，不認得的 PG* 變數也拒絕，連線前再用 libpq 自己的 PQconninfoParse 交叉比對。代價：開發者 shell 有多餘的 PG* 變數時，測試會拒絕執行，要先 unset。

2.3 CI 的防護目標：防疏忽，不防攻擊（D-044～D-046）

T-002 前兩輪都用「列舉禁止的語法」來寫檢查，Verifier 每一輪都找得到新的繞過，例如把 SQL 藏在單引號字串的函式本體、os._exit(0)。比較過的兩種做法：(A) 防疏忽，用禁止整類寫法加上比對結果；(B) 防到刻意攻擊，需要完整的語意分析，可能永遠補不完。Kuei 選了 A（issue #7）。結果：

  • migration：直接禁止函式、程序、trigger、DO、lo_*（D-045），另外在拋棄式 PG 17 上，用沒有 public 權限的角色實際執行 migration，比對 yc_v3 以外有沒有變化（D-042）。
  • 測試弱化：不再掃語法，改成比對結果（D-046）：目標分支上通過的每個測試 ID，在 PR 上都必須被收集而且通過。目標分支的結果在同一個 CI job 裡實際跑出來，不信任 PR 提供的檔案。

會出問題的情況：斷言被放寬但測試 ID 不變時，CI 抓不到，只能靠 Verifier 審查 diff；刻意構造的繞過也一樣。

2.4 commit-author 依帳號判斷，不依 email（D-039）

Chief 用 GitHub API 合併 PR #2 時，產生的 merge commit 84852d9 作者 email 是 bullet-bots 帳號的主要 email，不是 noreply。比 email 的話，milestone/M0 → main 會固定失敗，而且依規則不能改寫歷史。改成用 GitHub API 讀每個 commit 的 author.login。T-002 的 Builder 與 Verifier 都已確認 origin/main..origin/milestone/M0 會通過。

2.5 「nothing is written」比對資料庫內容（T-003）

共用步驟在動作前後各取一次 yc_v3 所有資料表的快照並比對，不只看回應。nothing else is written 只扣掉同一個 scenario 前面明確斷言過的寫入，例如 AUD-R03 的 ACCESS_DENIED 那一列；第 1 輪曾把兩者做成同一個步驟，被 Verifier 判 FAIL。快照不比對 identity sequence 的值，因為被回滾的 insert 也會讓序號前進。

2.6 稽核類型用 CHECK 約束（T-003，migration 0002）

附錄 C 的 37 種類型寫成 audit_log.type 的 CHECK 約束，而不是另建對照表或 PG enum。理由：類型由規格固定，CHECK 在 migration 裡最容易逐字對照附錄 C。代價：新增類型要寫 migration 修改約束。actor_name 另外存一份名字，讓稽核不隨帳戶改名而變。

10. 這個 milestone 的學習重點

10.1 fail-closed 與允許清單

安全檢查遇到「不確定」時，要判為拒絕，而不是放行。這個專案有三個地方用到：本機資料庫防線、CI 的分支名稱與 SQL 檢查、evidence 缺少 screens 欄位。T-001 兩輪的 FAIL 都是黑名單漏掉某一種寫法，改成允許清單後才收斂。

10.2 檢查「結果」比檢查「語法」可靠

「測試沒被弱化」用語法掃描永遠列舉不完；改成比對「目標分支上通過的測試在 PR 上是否仍然通過」後，不管用什麼寫法讓測試消失都會被抓到。同樣的想法也用在 migration 的沙盒：直接執行，再比較執行前後的差異。

10.3 防護目標（threat model）要先定義

T-002 花了三輪，原因不是能力不足，而是「要防到什麼程度」沒有定義，驗證者可以無限升級攻擊。定義「防疏忽、不防攻擊」之後，一輪就通過。這也說明了自動檢查和人工審查的分工：自動檢查擋常見的錯，人工審查擋刻意的繞過。

10.4 規格矛盾只有實際跑過才會發現

IAM-F03 與 AUD-R03 的矛盾（issue #9）、CFG-F02 的同名 scenario，都是在把 spec 交給程式執行時才浮現。測試全綠只代表符合規格，不代表規格本身是對的。
