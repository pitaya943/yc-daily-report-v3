2. 為何這樣設計

2.1 IAM 三張依序進行，而不是 T-102 與 T-103 平行（D-055）

原本的計畫是 T-102 和 T-103 平行。檢查後發現：鎖定要掛在登入流程上，「已登入者開登入頁會被轉走」也在登入模組裡，所以兩張都要改 app/modules/iam/sign_in/，平行會互相衝突。改成 T-101 → T-103 → T-102。T-103 排前面，因為 M2 的 T-201 依賴它；T-102 最難（並行 scenario），卡住也不會擋到 M2。代價：IAM 這條線沒有平行，M1 的總時間變長。後來 T-102 真的因為兩個 issue 停了兩次，這個排序讓那段時間沒有擋住其他工作。

2.2 共用的 session 程式放在 app/core/session.py

之後每個模組都要知道「現在是誰」。比較過兩種做法：(A) 放在 app/core，每個模組都經由同一個 FastAPI dependency 取得行為者；(B) 放在 IAM 模組裡，其他模組跨模組 import。選 A：閒置逾時、CSRF、session 失效都集中在一個 dependency，沒有模組能繞過，也不必修改 app/main.py。會出問題的情況：如果之後有端點沒有使用這個 dependency，它就沒有受到保護。這件事要由 M6 的權限矩陣（T-603）檢查。

2.3 密碼雜湊用標準庫 scrypt（D-056）

比較過 scrypt（標準庫）、Argon2id（第三方 argon2-cffi）、bcrypt。選 scrypt：不新增依賴，參數採 OWASP 最低建議（N=2^17、r=8、p=1），雜湊字串帶演算法前綴，日後可以漸進換演算法。bcrypt 會截斷超過 72 bytes 的密碼，30 個中文字可能踩到。代價：每次登入約 128 MiB 記憶體與 0.3 秒 CPU。T-103 因此把登入改到 threadpool 執行，並限制同時最多 4 個 scrypt（T-103 Builder 自己的取捨，見第 6 節）。

2.4 鎖定與頻率限制的計數存在資料庫，不存在記憶體

規格要求計數「跨 worker 與重新啟動」（IAM-R07）。記憶體做不到，所以 migration 0004 建了兩張表，並用交易內的 advisory lock 避免競爭（不用 trigger，因為 D-045 禁止）。代價是測試要能分辨「計數真的在資料庫」：Verifier 發現單看 @concurrency 這個 scenario 分不出來，但整組測試分得出來（12 個變異都被抓到）。見 issue #23 第 6 項。

2.5 IAM-R10 延到 T-201，並用單元測試補上 M1 的驗證（D-058）

done-when 檢查以規則為單位：一條規則加進 implemented.txt，它底下的每個 scenario 都必須通過。IAM-R10 有一個 scenario 需要日報資料，M1 還沒有。比較過三種做法：(A) 延後規則 ID，M1 用單元測試驗證閒置邊界；(B) 改規格，把那個 scenario 移走；(C) 整張 T-103 延到 M2。你選了 A。代價：M1 的「逾時登出」只由 tests/unit/iam/ 把關；那些單元測試在 T-201 之前不能刪除或改名。

2.6 「被拒絕的登入不寫任何資料」改成「只寫失敗計數與嘗試紀錄」（D-069、D-077）

T-101 的 Builder 把 IAM-R03 寫得比規格嚴格：登入失敗時整個資料庫不變。但 T-102 依規格必須寫失敗次數與嘗試紀錄，兩者衝突，Builder 依規停下來找你兩次。你同意收窄：只排除 0004 的兩張表，其他表仍須完全不變；而且被排除的寫入要由 IAM-F02 明確斷言。學到的事：比規格更嚴的斷言不是免費的，它會變成後續 ticket 的地雷（pitfall #29）。

10. 這個 milestone 的學習重點

10.1 密碼雜湊為什麼要「慢」

一般的雜湊（SHA-256）設計成很快，攻擊者拿到資料庫後，每秒可以猜數十億次。scrypt 這類「記憶體困難」的函式，刻意讓每次計算都要大量記憶體（這裡是 128 MiB）與時間，所以 GPU 無法大量平行猜測。代價由伺服器承擔，所以要限制同時進行的數量，並避免在 async 路由裡直接計算（2.3 節）。

10.2 CSRF 與 SameSite cookie

瀏覽器會自動附上 cookie，所以惡意網站可以讓已登入的使用者「替它送出」請求。防法是：改變資料的請求要帶一個只有本站頁面拿得到的 token（這裡放在標頭 X-CSRF-Token），再加上 SameSite=Lax 讓跨站的 POST 不帶 cookie。D-053 讓這種被擋下的請求也寫稽核，偽造攻擊因此會留下紀錄。

10.3 以結果判定測試是否被弱化，以及「過度嚴格」的代價

no-weakened-tests 比對的是「目標分支上通過的測試，在 PR 上是否仍通過」，不看語法。所以分支落後時，別人新增的測試看起來就像「消失」（T-103 開 Verifier 前先合併 milestone 就是為此）。反過來，Builder 寫得比規格更嚴的斷言也會被 CI 保護，之後要放寬就得經過你（#20、#21）。測試越嚴不一定越好；嚴格的方向要和規格一致。

10.4 金額計算：不用浮點數、明確的四捨五入

0.1 + 0.2 ≠ 0.3 是浮點數的本質，所以金額全部用整數或分數（Fraction）計算。Python 的 round() 是「銀行家捨入」（2.5 → 2），而 AD-2 要求 half-up（2.5 → 3），所以用 (2x+1)//2 自己實作。「在哪一步捨入」也會改變結果：例如跨年的保留金，每年各自捨入再相加（D-071），和合併後才捨入，結果可能不同。

10.5 變異測試：驗證測試本身

Verifier 故意把產品程式改壞（例如 >= 改成 >），看測試會不會失敗。沒失敗的變異（「存活」）代表那個行為沒有被測試釘住。T-112 有 2 個存活，雖然實作是對的，但之後有人改壞也不會被發現，所以要在 T-402 補測試。
