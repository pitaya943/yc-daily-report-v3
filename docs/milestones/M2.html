2. 為何這樣設計

2.1 RPT-R12 與自訂工項：資料模型不提前替 M3 決定（D-085、D-086）

規劃時發現 M2 有兩處用到 M3 才建立的資料：RPT-R12 需要「保存的份額」，T-203 的篩選與匯出需要「自訂工項」。份額的結構取決於 REV-R11（確認時怎麼存），提前建表很可能要再改，所以把 RPT-R12 整條移到建立份額表的 T-301。自訂工項不同：REV-R20 規定一張回報最多一個，一對一放在 reports 上三個可為 null 的欄位最簡單，check 約束要求三者同時為 null 或同時有值；T-302 之後很可能不需要 migration。會出問題的情況：如果 M3 決定一張回報可以有多個自訂工項，這三個欄位要改成獨立的表。

2.2 共用版型負責 CSRF，各頁不自己處理（D-062、D-080、D-088）

T-200 把 htmx.org@2.0.11 原封不動放進 repo（Verifier 自己用 npm pack 比對 sha256 d6fdc75f…f717），並提供 render_page 與 base.html：已登入時在 <body> 放 hx-headers='{"X-CSRF-Token": …}'（用 Jinja 的 tojson 產生，放在單引號屬性內）。另一個做法是每張表單放隱藏欄位，但那樣 app/core/session.py 的檢查要讀請求主體，而且每張表單都可能忘記放。代價：沒有 JavaScript 的純 HTML 表單不能用（D-080 已接受）；HTMX 2 預設不顯示 4xx 回應，所以每頁要自己處理 htmx:beforeSwap（pitfall #31）。選 2.x 而不是 4.x：4.0 剛發布不久，是 npm 的 next。

2.3 每日 3 筆上限在並行時也成立：鎖住提交者的帳戶列

T-201 在同一個 transaction 裡先 select … for no key update 鎖住提交者在 accounts 的那一列，再計數、寫入、寫稽核、提交。沒有用 unique 約束，因為「最多 3 筆」不是唯一性；也沒有用 trigger，因為 D-045 不允許。代價是同一個人在不同日期的送出也會排隊，但量級可以忽略。會出問題的情況：之後有新的寫入路徑（例如 M3 的管理員代填）沒有拿同一把鎖。另外，RPT-R04 的並行 scenario 只送 2 個請求，Verifier 拿掉鎖之後 15 次只抓到 10 次（見第 8 節）。

2.4 改了已實作的規則時，先暫時移出再由新 ticket 加回（D-103）

issue #29 的 2B 改寫了 RPT-R05（不符資格的共同作業者從「略過」改為「拒絕」），1B 讓 RPT-R03 的邊界表也要改寫。這兩條規則已經實作，規格一改、程式還沒改之前，milestone/M2 的 CI 會變紅，擋住所有 ticket。你選了「暫時移出 implemented」：Chief 在改規格的同一個 commit（ef17f8e）把 RPT-R03、R05 移出 tests/implemented.txt，並刪除兩個寫死舊行為的補充測試；T-204 加回，done-when 強制全部通過。代價：從 ef17f8e 到 T-204 合併（cc9101e）之間，這兩條規則沒有 Gherkin 把關。另一個做法是把規格修改放在 T-204 的分支上，但同一個 PR 會混著 Chief 的規格修改與 Builder 的程式，Verifier 較難分辨。

2.5 共用步驟從「只有一種情況」一般化（D-093、D-094、D-095）

M1 把 the outcome is <OUTCOME> 一般化時，只考慮了 LOCKED：其他類別一律要求錯誤字串為 null、資料完全不變。M2 碰到三個反例：附錄 B 有字串的 INVALID（#27）、規格要求寫 ACCESS_DENIED 的 FORBIDDEN（#31），以及只看 REPORT_CREATE 的 the audit description contains（#30）。三次都選擇修改共用步驟，而不是改規格：因為同樣的寫法在 M3～M5 的 CFG、IAM-F04、MAT、LED、AUD 都會出現，改規格要一個一個改。代價：the outcome is INVALID 現在只確認「是附錄 B 的某一句」，不確認是「這個欄位的那一句」；逐字對到正確的句子，由各 feature 的 … with message "…" scenario 負責。每次修改都加了反例單元測試，證明沒有放寬到「任何字串都通過」。

2.6 匯出用 openpyxl（D-087）

比較過用標準庫 zipfile 自己寫 xlsx：不新增依賴，但格式要自己維護，Excel 能不能開只能靠截圖。選了 openpyxl>=3.1.5,<3.2，M4 的薪資批次匯出可以沿用。T-203 另外處理了試算表注入：使用者輸入的文字一律存成字串型別，不會被當成公式（有測試）。

10. 這個 milestone 的學習重點

10.1 為什麼「先查再寫」擋不住並行

「查詢今天已有幾筆，少於 3 才寫入」在兩個請求同時進行時會失效：兩個請求都在對方寫入前查到 2 筆，於是都寫入，變成 4 筆。這叫 check-then-act 的競爭條件。解法是讓「查」與「寫」之間不能插隊：這裡在同一個 transaction 裡先鎖住提交者的帳戶列（select … for no key update），第二個請求必須等第一個提交後才能查，所以會查到 3 筆而被拒絕。也可以用資料庫約束，但「最多 3 筆」不是 unique 能表達的。

10.2 CSRF token 放在標頭，而不是表單

M1 已經說明 CSRF 是什麼（M1 報告 10.2）。M2 決定的是 token 怎麼送：放在每個請求的標頭 X-CSRF-Token，由共用版型的 hx-headers 統一加上，所以伺服器檢查時不必讀請求主體，各頁也不會忘記放。惡意網站可以讓瀏覽器送出跨站的表單，但不能替請求加上自訂標頭（瀏覽器的同源政策會擋），所以只要 token 在標頭，偽造的請求就不會通過。代價是沒有 JavaScript 的純表單無法使用。

10.3 改規格時，已經通過的測試怎麼辦

CI 的 no-weakened-tests 保護的是「已經通過的測試不能消失或變失敗」。這擋住了偷懶的 agent，但也代表規格改變時，寫死舊行為的測試會反過來擋住正確的新程式。M2 碰到兩次：T-201 的補充測試（Chief 依 D-103 刪除）與 T-202 的補充測試（第 1 輪 FAIL）。教訓是：測試應該只斷言規格寫的事；規格沒寫、或可能改變的行為，不要寫成測試。

10.4 共用測試步驟是公開介面

pytest-bdd 的步驟是全域註冊的，同一句話在所有 feature 都會用到同一個定義。所以共用步驟的語意一旦定下，之後每個 feature 都要遵守；寫得太窄（只看 REPORT_CREATE）或太嚴（FORBIDDEN 不准寫任何資料），就會在之後的 milestone 一再卡住。M2 的三次修改（D-093～D-095）都伴隨反例測試，證明放寬的只是規格允許的部分。

10.5 匯出檔的試算表注入

如果使用者在名稱欄位輸入 =HYPERLINK("http://…")，而匯出時把它當成公式寫入，別人打開 Excel 時就可能被誘導點擊或執行。T-203 把所有使用者輸入的文字明確存成字串型別。這也是「伺服器不信任任何輸入」的延伸：不只驗證進來的資料，也要注意資料被其他程式讀取時的意義。
