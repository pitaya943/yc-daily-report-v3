3. 每個拒絕案例斷言三件事：結果類別、完整錯誤字串、資料沒有任何變動。
4. 伺服器重新驗證每個欄位；缺少的值不以預設值補上。
5. 回報記下送出當時的工項組（AD-4）。
6. 頁面（D-057）：`GET /reports` 是 USER 登入後的落地頁，顯示日報表單；`POST /reports` 送出。頁面用 T-200 的 `app/core/pages.py` 與 `base.html`，表單用 HTMX 送出，anti-forgery token 由版型的 `hx-headers` 帶上（D-080），不另外放隱藏欄位。受保護的端點都經過 `get_current_actor`。
   - HTMX 2 預設不把 4xx 回應換進畫面（T-200 Verifier 的發現）。拒絕時使用者必須在畫面上看到完整的錯誤字串：在這張 ticket 自己的模板裡處理（例如 `htmx:beforeSwap` 讓 4xx 也 swap 到錯誤區塊），不得修改 `app/core/templates/base.html`。
7. 資料模型（migration `0005`）：
   - 回報的狀態欄位涵蓋 `spec/state-machines.md` 的全部狀態（`PENDING`、`CONFIRMED`、`REJECTED`），以 check 約束限制；這張 ticket 只會寫入 `PENDING`，其他狀態由 T-202、T-203 的 Given 步驟直接寫入資料庫、M3 的 T-301 實作轉移。
   - 共同作業者依提交者選擇的順序保存（RPT-R05）。
   - 自訂工項（REV-R20：每張回報最多一個）以 `reports` 上可為 null 的三個欄位保存：名稱（最多 100 字）、數量（0.1 只的整數，0～9999）、單價（≥ 0 的整數），以 check 約束要求三者同時為 null 或同時有值。這張 ticket 不寫入它們；T-203 的篩選與匯出、M3 的 T-302 使用（D-086）。
   - 每日上限（RPT-R04）在並行時也成立（`@concurrency` scenario），做法寫在 PR 說明。
   - 工項目錄（附錄 A）怎麼保存由 Builder 決定，寫在 PR 說明的「需要 Kuei 知道的設計選擇」。
   - 欄位驗證、工項目錄與回報的讀寫寫成可被 T-202（編輯）與 T-203（歷史）import 的函式（放在 `app/modules/reports/submit_a_daily_report/` 的 `service.py`、`repo.py`），讓後面的 ticket 不必修改這個目錄。PR 說明列出這些函式。
