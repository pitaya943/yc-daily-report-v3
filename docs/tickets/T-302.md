## 完成條件

1. 下列規則的 7 個 scenario 全部通過，而且在實作前先確認它們會失敗：`REV-R20`（3）、`REV-R21`（1）、`REV-R22`（1）、`REV-R23`（1）、`REV-R24`（1）。
2. 這些規則 ID 已加入 `tests/implemented.txt`。
3. 每個拒絕案例斷言三件事：結果類別、完整錯誤字串、資料沒有任何變動。
4. 伺服器重新驗證每個欄位；缺少的值不以預設值補上。
5. CI 全綠。
6. 每一條完成條件都附上證據：CLI 輸出貼在 PR 說明；有畫面的功能附截圖，存在 `docs/evidence/T-302/`。
7. PR 說明依 `.github/PULL_REQUEST_TEMPLATE.md` 填寫。
8. 附加、取代、移除自訂工項時，先用 T-202 與 T-301 同一把鎖鎖住該回報（`app/modules/reports/report_lifecycle/repo.py` 的 `for update`，呼叫同一個函式）。回報不是 PENDING 時（AD-10），回到 PENDING 與刪除份額呼叫 T-301 已有的函式，不另寫一份。
9. 步驟 `audit rows "…" and "…" are written` 已由 T-301 為 RPT-R12 定義（步驟是全域註冊的，pitfall #26），直接使用，不要重複定義。
10. 至少一個工項（D-112）：附加、取代或移除自訂工項後，回報若沒有任何數量 > 0（一般工項全為 0，且沒有自訂工項或其數量為 0），拒絕為 `INVALID`「請至少填寫一個工項數量」，資料不變；判斷呼叫 `app/modules/reports/submit_a_daily_report/service.py` 的 `require_a_quantity`，不另寫一份。補充測試兩個方向：自訂工項是唯一的數量時移除被拒；有一般工項時移除成功。REV-R22 的步驟使用的回報要先有一個數量 > 0 的一般工項。
11. 「計算薪資」的讀取函式（D-111）：T-301 已在 `app/modules/review/crew_split_and_stored_shares/` 提供；這張 ticket 把自訂工項金額（每人的份額 × 這個工項自己的單價）加進去，REV-R23 的步驟呼叫它。這是 T-301 的目錄，只能新增與這項有關的內容，不改既有行為。
12. 路徑（D-118）：`POST /review/reports/{id}/custom-item`。
