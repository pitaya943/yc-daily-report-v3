## 完成條件

1. 下列規則的 6 個 scenario 全部通過，而且在實作前先確認它們會失敗：`RPT-R10`（2）、`RPT-R11`（3）、`RPT-R13`（1）。
   - RPT-R12 的 scenario 需要保存的份額，份額表由 M3 的 T-301 建立，所以 RPT-R12 改由 T-301 轉綠（D-085）。這張 ticket 仍實作管理員的編輯：依 `spec/state-machines.md`，CONFIRMED 的回報被管理員編輯後回到 PENDING，並寫 REPORT_UNCONFIRM 與 REPORT_UPDATE 兩筆稽核；刪除份額由 T-301 補上。
2. 這些規則 ID 已加入 `tests/implemented.txt`。
3. 每個拒絕案例斷言三件事：結果類別、完整錯誤字串、資料沒有任何變動。
4. 伺服器重新驗證每個欄位；缺少的值不以預設值補上。
5. 頁面與端點（D-057）：`GET /reports/{id}/edit`、`POST /reports/{id}`（編輯）、`POST /reports/{id}/delete`（刪除）。USER 與管理員用同一組端點，權限依角色與回報狀態在伺服器判斷。頁面用 T-200 的共用版型，表單用 HTMX 送出（D-080）。受保護的端點都經過 `get_current_actor`。
   - HTMX 2 預設不把 4xx 回應換進畫面（T-200 Verifier 的發現）。拒絕時使用者必須在畫面上看到完整的錯誤字串：在這張 ticket 自己的模板裡處理（例如 `htmx:beforeSwap` 讓 4xx 也 swap 到錯誤區塊），不得修改 `app/core/templates/base.html`。
6. 編輯的欄位驗證重用 T-201 的程式，不複製一份；需要讓 T-201 的程式可重用而必須修改 `app/modules/reports/submit_a_daily_report/` 時，停下來告訴 Chief（不在這張 ticket 的範圍）。
7. 測試步驟：CONFIRMED、REJECTED 的回報由 Given 步驟直接寫入資料庫（狀態轉移由 M3 實作）。不得定義與 `tests/steps/common/`、`tests/steps/RPT-F01/` 同文字的步驟（pitfall #26）；新增步驟前先 `grep`。
8. 比規格更嚴格的斷言要在 PR 說明列出（pitfall #29）。另外依 Kuei 的決定修改兩個共用步驟，只能做這兩項修改，PR 說明逐條寫出修改前後的差異（D-091）：
   - D-094：把 `the audit description contains "{text}"` 從 `tests/steps/RPT-F01/rpt_f01_steps.py` 搬到 `tests/steps/common/audit_description.py`（照 `tests/steps/common/` 其他檔案的註冊方式），新定義為「這個動作恰新增 1 列稽核，而且那一列的說明包含指定文字，不限類型」。`rpt_f01_steps.py` 只刪除這一個步驟，其他不動；RPT-R07 仍要通過。
   - D-095：`tests/steps/common/outcome.py` 的 `the outcome is FORBIDDEN` 改為「恰好新增 1 列 `ACCESS_DENIED`、行為者是被拒絕的人，其他資料表完全不變」；其他類別不變；D-093 的錯誤字串規則照舊。在 `tests/steps/common/test_outcome_messages.py` 加反例：沒寫 `ACCESS_DENIED`、寫了兩列、行為者不對、動到其他資料表，都必須失敗。
